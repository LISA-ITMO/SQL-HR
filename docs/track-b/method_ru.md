# Трек B: спецификация метода

> Справочная постановка широкого трека B от сентября 2026. Актуальный объём первого этапа и порядок подготовки к созвону — в [README 02.1](02.1_neurosymbolic_evidence_assessment/README.md). Заявления об отсутствии аналогов в этой ранней версии требуют проверки по текущему обзору литературы.

**Источники КРМ:** описание структуры и шкал ниже относится к ИТМО 3.0. В коллекции также появилась КРМ МФТИ по ИТ — потенциальный второй источник для расширения охвата профессий ИТ и ИИ. Её структуру, версии и соответствия с ИТМО ещё нужно проверить; индикаторы и уровни нельзя автоматически объединять. Сохранять модель-источник, версию и исходный идентификатор для каждой роли и оценки. Сначала аудит и ограниченный пилот, затем решение о проверке переноса метода между моделями. Подробности: [КРМ / frameworks](frameworks/README.md).

## 1. Обзор

**Цель:** операционализировать ролевые профили КРМ 3.0 для оценки кандидатов на основе подтверждающих свидетельств.

**Основная идея:**
```
Роль КРМ
→ Целевой уровень «роль–компетенция»
→ Целевой профиль на уровне индикаторов [выводится предлагаемым методом]

Кандидат
→ Артефакт-свидетельство
→ Фрагмент свидетельства
→ Релевантность индикатору
→ Достаточность свидетельства
→ Подтверждённый уровень владения
→ Разрыв / Неопределённость
```

## 2. Сущности

### 2.1 Сторона роли

| Сущность | Описание | Источник |
|----------|----------|----------|
| **Роль** | Профессиональная роль (например, «ML Engineer») | КРМ 3.0 |
| **Компетенция** | Область навыков / знаний / способностей | КРМ 3.0 |
| **Индикатор** | Наблюдаемое проявление компетенции | КРМ 3.0 (подлежит извлечению) |
| **Целевой уровень** | Требуемый уровень индикатора: Б / С / П | Выводится из целевых уровней «роль–компетенция» КРМ посредством явной политики, валидированной экспертами |

### 2.2 Сторона кандидата

| Сущность | Описание | Источник |
|----------|----------|----------|
| **Кандидат** | Соискатель / сотрудник | Профиль кандидата |
| **Подтверждающее свидетельство** | Документированный артефакт, демонстрирующий компетенцию | CV, портфолио, сертификации |
| **Подтверждённый уровень** | Уровень владения, подтверждаемый артефактом | Извлекается из свидетельства |
| **Разрыв** | Порядковое отставание от целевого уровня; неопределённость фиксируется отдельно | Предлагаемая политика оценки |

## 3. Семантика оценки

### 3.1 Состояния оценки

**Трёхсостояниeвая модель (НЕ бинарная):**

| Состояние | Значение |
|-----------|----------|
| **SUPPORTED_AT_TARGET** | Свидетельства подтверждают целевой уровень или уровень выше целевого |
| **SUPPORTED_BELOW_TARGET** | Свидетельства имеются, но подтверждённый уровень ниже целевого |
| **UNKNOWN** | Релевантные свидетельства отсутствуют либо их недостаточно, чтобы присвоить подтверждённый уровень |

**Ключевой принцип:** UNKNOWN ≠ отсутствие компетенции. Это означает недостаточность подтверждающих свидетельств.

### 3.2 Предикат оценки

```
Assess(candidate, indicator, target_profile) → {
  state: SUPPORTED_AT_TARGET | SUPPORTED_BELOW_TARGET | UNKNOWN,
  evidence: [список подтверждающих артефактов],
  demonstrated_level: Б | С | П | null,
  target_level: Б | С | П,
  shortfall: {demonstrated_level, target_level} (если SUPPORTED_BELOW_TARGET; иначе null)
}
```

## 4. Моделирование подтверждающих свидетельств

### 4.1 Типы свидетельств

| Тип | Примеры |
|-----|---------|
| **Опыт работы** | Должности, обязанности, достижения |
| **Проекты** | Личные / профессиональные проекты, GitHub-репозитории |
| **Образование** | Дипломы, курсы, программы обучения |
| **Сертификации** | Профессиональные сертификаты, бейджи |
| **Публикации** | Статьи, посты в блогах, доклады |
| **Прочее** | Награды, хакатоны, соревнования |

### 4.2 Свойства свидетельства

```
Evidence = {
  evidence_id: string,
  type: work | project | education | certification | publication | other,
  source: string,
  date_or_period: optional,
  raw_text_or_description: text,
  provenance: metadata
}
```

### 4.3 Извлечение свидетельств

**Требует разработки:**
- ручное аннотирование (пилотное исследование);
- извлечение на основе LLM (будущая работа);
- гибридный подход (извлечение с помощью LLM + валидация человеком).

## 5. Анализ разрывов в компетенциях

### 5.1 Вычисление разрыва

```
Gap(candidate, role) = {
  competency_gaps: {
    competency_id: {
      target_level: Б | С | П,
      demonstrated_level: Б | С | П | null (требует валидированной политики агрегации),
      assessment_state: SUPPORTED_AT_TARGET | SUPPORTED_BELOW_TARGET | UNKNOWN,
      indicators: {
        indicator_id: {
          state: SUPPORTED_AT_TARGET | SUPPORTED_BELOW_TARGET | UNKNOWN,
          evidence: [...]
        }
      }
    }
  },
  overall_gap_score: aggregate(competency_gaps)
}
```

### 5.2 Проблема агрегации

**Открытый вопрос:** как агрегировать оценки на уровне индикаторов в разрыв на уровне компетенции?

**Варианты:**
- минимум (уровень компетенции определяется самым слабым индикатором);
- доля индикаторов, подтверждённых на целевом уровне, при этом UNKNOWN сообщается отдельно;
- взвешенное покрытие индикаторов, подтверждённых на целевом уровне (веса требуют обоснования);
- байесовская агрегация (распространение неопределённости).

**Решение:** требуется экспертная политика или эмпирическая валидация. Б < С < П — порядковая шкала. Равенство расстояний между соседними уровнями не установлено; вычитание и усреднение кодов уровней не являются операциями по умолчанию. Любые числовые стоимости переходов представляют собой отдельную предлагаемую политику и требуют валидации. UNKNOWN не является нулём или дополнительным уровнем владения.

## 6. Ранжирование

### 6.1 Функция ранжирования

```
Score(candidate, role) = f(competency_gaps)
```

**Возможные функции:**
- взвешенная стоимость переходов от уровня ниже целевого к целевому — только после валидации явной политики стоимости;
- количество компетенций в состоянии AT_TARGET;
- покрытие свидетельствами / частота UNKNOWN сообщаются отдельно; любой штраф в ранжировании требует явной валидации и не должен интерпретироваться как отсутствие компетенции;
- гибридная функция (комбинация перечисленного выше).

### 6.2 Бейзлайны

Для оценки:
1. BM25 / лексическое сопоставление с профилем роли;
2. плотное семантическое сопоставление (эмбеддинги);
3. пересечение плоских списков навыков / компетенций;
4. сопоставление на уровне компетенций без индикаторов;
5. предлагаемая модель подтверждающих свидетельств на уровне индикаторов.

## 7. Объяснимость

### 7.1 Типы объяснений

| Тип | Шаблон |
|-----|--------|
| **Подтверждено на целевом уровне** | «Кандидат демонстрирует {Competency} на уровне {Level}, что подтверждается {Evidence}» |
| **Подтверждено ниже целевого уровня** | «Кандидат демонстрирует {Competency} на уровне {Level}, однако для роли требуется {Target Level}. Переход от подтверждённого уровня к целевому: {Level} → {Target Level}» |
| **Неизвестно** | «Имеющиеся свидетельства отсутствуют или недостаточны для оценки {Competency/Indicator}. Необходимы дополнительные свидетельства: {Evidence types}» |

### 7.2 Цепочки происхождения

```
Кандидат
  │
  ├─[HAS_EVIDENCE]→ Evidence_1
  │   └─[SUPPORTS]→ Indicator_A → Competency_X → Целевой уровень С
  │       └─ Состояние: SUPPORTED_AT_TARGET
  │
  ├─[HAS_EVIDENCE]→ Evidence_2
  │   └─[SUPPORTS]→ Indicator_B → Competency_Y → Целевой уровень П
  │       └─ Состояние: SUPPORTED_BELOW_TARGET (подтверждён Б)
  │
  └─[MISSING]→ Indicator_C → Competency_Z
      └─ Состояние: UNKNOWN
```

## 8. Связь с SQL-HR

### 8.1 Наследование

**SQL-HR предоставляет:**
- типизированное представление ограничений;
- разделение жёстких и мягких ограничений;
- слой политики Ideal / Fit / Fallback.

**Трек B расширяет:**
- от реляционных предикатов → к оценке на основе подтверждающих свидетельств;
- от точного совпадения → к анализу разрыва на порядковой шкале;
- от бинарного удовлетворения → к трёхсостояниевой оценке (AT_TARGET / BELOW / UNKNOWN).

### 8.2 Точки интеграции

**Возможная архитектура:**
```
Запрос рекрутера
    │
    ├─→ Слой SQL-HR (жёсткие / мягкие ограничения → допустимость кандидата)
    │
    └─→ Слой КРМ (профиль компетенций → ранжирование по разрыву)
```

**Ideal / Fit / Fallback:**
- вторичный слой политики поверх ранжирования по разрыву КРМ.

## 9. Примечания по реализации

### 9.1 Графовое представление (опционально)

**При использовании графовой БД:**
- узлы: Role, Competency, Indicator, Candidate, Evidence;
- рёбра: REQUIRES, SUPPORTS, DEMONSTRATES и т. д.

**При использовании реляционной БД:**
- таблицы для каждого типа сущностей;
- JOIN-операции для связей.

**Ключевой момент:** граф — это выбор реализации, а не основная научная новизна.

### 9.2 Шкала уровней КРМ 3.0

В текущих детализированных листах КРМ 3.0 используются:

`Б / С / П` = `базовый / средний / продвинутый`.

Каждый индикатор содержит текстовые поведенческие якоря для этих трёх уровней.

Метод должен сопоставлять подтверждающие свидетельства кандидата с этими якорями, а не с искусственно введённой универсальной шкалой L1–L5.

### 9.3 Представление индикаторов

Индикаторы явно присутствуют в КРМ 3.0 и должны импортироваться напрямую из соответствующих листов компетенций.

Методологические вопросы состоят в следующем:
- как сопоставлять подтверждающие свидетельства кандидата с индикатором;
- как оценивать достаточность свидетельств;
- как присваивать подтверждённый уровень Б / С / П;
- как выводить целевые требования на уровне индикаторов из агрегированного уровня «Роль × Компетенция».
